## 1. Objective & Scope

### 1.1 Objective
Provide a minimal, auditable Soroban contract that lets the ODRM backend **anchor** the 32-byte evidence commitment for a detection record on Stellar Testnet, and lets any party **verify** that a given detection ID was anchored with a given commitment.

The contract stores **commitments only** — never coordinates, PII, payloads, or detection metadata.

### 1.2 In scope (D5)
- Self-contained Rust crate at `contracts/valoris-evidence/`.
- Domain-separated leaf/node hashing that is **byte-identical** to `backend/src/odrm/evidence/service.py` (`_leaf_node`, `_parent_node`).
- `register_evidence` (admin-authorized, append-only) and `verify_evidence` (permissionless, read-only).
- Typed errors, input validation, storage TTL policy, registration event.
- Rust unit tests including cross-language golden vectors.
- Testnet build + deploy + invoke runbook.
- `.gitignore` hygiene and a scoped CI workflow (repo currently has none).

### 1.3 Out of scope (explicitly deferred)
- On-chain Merkle **root** batching and proof verification (D6 candidate).
- Backend signer/outbox integration and the API endpoint that submits registrations.
- Frontend surfacing of on-chain proofs.
- Mainnet deployment, key custody/HSM, multisig admin, contract upgrade/migration strategy.
- Any change to D2 hashing behavior.

- `rlib` is included so the backend parity harness and future fuzz targets can link the crate; note the known Cargo LTO limitation for mixed `cdylib`+`rlib` and build via `stellar contract build` (which avoids it).

### 5.2 Domain separation (must mirror D2 exactly)

Backend reference (`backend/src/odrm/evidence/service.py:17-18,83-90`):

```python
LEAF_PREFIX = b"\x00"
NODE_PREFIX = b"\x01"

def _leaf_node(screening_hash: str) -> bytes:
    return hashlib.sha256(LEAF_PREFIX + bytes.fromhex(screening_hash)).digest()

def _parent_node(left: bytes, right: bytes) -> bytes:
    return hashlib.sha256(NODE_PREFIX + left + right).digest()
```

Contract mirror:

```rust
pub const LEAF_PREFIX: [u8; 1] = [0x00]; // directive notation [0u8] -> valid Rust [0u8; 1]
pub const NODE_PREFIX: [u8; 1] = [0x01];

// leaf(x)  = SHA-256( 0x00 || x_raw32 )
// node(l,r)= SHA-256( 0x01 || l || r )
```

Three parity rules that the implementation and tests must enforce:

1. **Raw bytes, not ASCII hex.** D2 calls `bytes.fromhex(screening_hash)` *before* prefixing. The contract therefore hashes the 32 decoded bytes. Passing the 64-character hex string across the ABI produces a different commitment and silently breaks referential integrity. The backend adapter must `bytes.fromhex(...)` first; the contract rejects any `Bytes` whose length is not exactly 32.
2. **Single-byte prefixes.** `[0u8]` in the directive is pseudo-notation; Rust requires a sized array (`[0u8; 1]`) or a scalar (`0u8`).
3. **Odd-node promotion is unchanged** (D2 promotes the last node to the next level). The contract does not build trees in D5, but `node_hash` is implemented and tested now so D6 cannot introduce a divergent convention.

### 5.4 Public interface

```rust
pub fn __constructor(env: Env, admin: Address);

pub fn register_evidence(
    env: Env,
    detection_id: String,
    evidence_hash: Bytes,        // exactly 32 raw bytes (screening hash, hex-decoded)
) -> Result<(), Error>;

pub fn verify_evidence(
    env: Env,
    detection_id: String,
    expected_hash: Bytes,        // exactly 32 raw bytes
) -> bool;

// Read-only helper: returns the leaf commitment for a 32-byte hash.
// Public hash function, no secret; used by tests and off-chain parity checks.
pub fn leaf_commitment(env: Env, evidence_hash: Bytes) -> Result<BytesN<32>, Error>;
```

Design notes:
- **Authorization without changing the required signature.** Soroban has no `msg.sender`; the admin is stored at construction and `register_evidence` calls `admin.require_auth()`. The signature therefore stays exactly as specified in the acceptance criteria.
- **Constructor, not `initialize`.** The host runs `__constructor` atomically at deploy, so there is no initializer to front-run.
- **`Bytes` at the ABI, `BytesN<32>` internally.** Matches the required signature while retaining type safety; length is validated before conversion.
- **`verify_evidence` never panics on input.** Malformed length or unknown ID returns `false`, making it safe as a cross-contract predicate.
- **Append-only.** A second registration for an existing `detection_id` returns `Err(AlreadyRegistered)`; there is no overwrite path in D5. Corrections require a future versioned key and are out of scope.
- **Event.** `register_evidence` publishes an `("evidence", "register")` event containing `(detection_id, commitment)` for off-chain indexer reconciliation.

### 5.5 Storage, validation, errors

```rust
#[contracttype]
#[derive(Clone)]
pub enum DataKey { Admin, Evidence(String) }

#[contracttype]
#[derive(Clone)]
pub struct EvidenceRecord {
    pub commitment: BytesN<32>,
    pub registered_at: u64,     // env.ledger().timestamp()
    pub registered_ledger: u32, // env.ledger().sequence()
}

#[contracterror]
#[derive(Copy, Clone, Debug, Eq, PartialEq)]
#[repr(u32)]
pub enum Error {
    AlreadyRegistered   = 1,
    InvalidHashLength   = 2,
    InvalidDetectionId  = 3,
    NotInitialized      = 4,
}
```

- **Durability:** `DataKey::Admin` in instance storage; `DataKey::Evidence(id)` in **persistent** storage (must survive archival windows).
- **TTL:** `extend_ttl(threshold, extend_to)` on both write and read paths. Target values: threshold 518,400 ledgers (~30 days at 5s close), extend-to 3,110,400 ledgers (~180 days). Values are clamped/validated against the network `max_entry_ttl` during Testnet bring-up; the confirmed values are recorded in the Phase 5 report.
- **Validation:** `detection_id` must be 1–64 bytes of UTF-8; `evidence_hash`/`expected_hash` must be exactly 32 bytes. Violations return typed errors (write path) or `false` (read path).
- **No unbounded loops, no dynamic allocation of unbounded size, no `std`.**

## 7. Build & Deploy Runbook (Stellar Testnet)

### 7.1 ⚠️ Mandatory correction to the acceptance criterion
The directive specifies `cargo build --target wasm32-unknown-unknown`. Per Stellar documentation, **that target is not supported for Soroban contracts on Rust 1.82+** — it enables `reference-types`/`multi-value`, which the Soroban runtime rejects and which the SDK build script errors on. The supported target is `wasm32v1-none` (Rust ≥ 1.84), and `stellar contract build` selects it and applies the required settings automatically.

This is the one deliberate deviation from the acceptance criteria and it is non-negotiable for a deployable artifact. It is flagged here for CTO sign-off.

### 7.2 Prerequisites
```bash
rustup target add wasm32v1-none     # Rust >= 1.84
stellar --version                   # stellar-cli required for build/deploy/invoke
```

### 7.3 Build
```bash
cd contracts/valoris-evidence
stellar contract build
# artifact: target/wasm32v1-none/release/valoris_evidence.wasm

# explicit cargo equivalent (supported target, not wasm32-unknown-unknown)
cargo build --target wasm32v1-none --release
```

### 7.4 Deploy to Testnet
```bash
# throwaway Testnet identity (D5 only; custody design is out of scope)
stellar keys generate odrm-d5-deployer
stellar keys fund odrm-d5-deployer

stellar contract deploy \
  --wasm target/wasm32v1-none/release/valoris_evidence.wasm \
  --source odrm-d5-deployer \
  --network testnet \
  --alias valoris_evidence \
  -- --admin <ADMIN_G_ADDRESS>
```

## 8. Standard Audit Readiness Impact

### 8.1 Repo Hygiene
- Isolated crate at `contracts/valoris-evidence/` with its own `Cargo.toml`/`Cargo.lock` and an empty `[workspace]` table; no root Rust workspace, no coupling to the Python backend.
- Root `.gitignore` gains `contracts/**/target/`; build artifacts never enter history. `Cargo.lock` is committed for reproducible dependency resolution.
- No dead code: every public item is exercised by a test; the only optional helper (`leaf_commitment`) is read-only and tested.
- No changes to existing application code, migrations, or docs.

### 8.2 Integration Tests
- 12 Rust `#[test]` cases covering hash parity, prefix separation, registration, duplicate rejection, auth, validation, and permissionless verification (§6).
- A backend Python parity test pins the same golden vectors, so a change to either hash implementation fails CI.
- CI step `cargo test` runs on every change under `contracts/**`; the repo has no workflows today, so this workflow is created with a narrow path filter to avoid touching unrelated pipelines.

### 8.3 Threat Model / Dataflow
```
PostgreSQL (detection records, D2 screening hashes)
   │  system of record for content
   ▼
Backend evidence service  ── canonical JSON → input/output hash → screening_hash
   │  _leaf_node: sha256(0x00 ‖ raw32)
   ▼
Registration adapter (D6; admin-signed tx)
   │  trust boundary: only 32 bytes cross; no coordinates, no PII, no payloads
   ▼
Soroban contract (Testnet)  ── persistent commitment, append-only, admin-authorized
   │
   ▼
verify_evidence (permissionless read) → API / consumer / auditor
```

- **Trust boundary:** the ledger attests *"this commitment was registered by the admin at ledger N"*. It does **not** attest that the off-chain evidence is truthful or that the hash corresponds to real sensor data — that is D2's canonicalization and the ingestion pipeline's responsibility. No oracle exists; this limitation is documented in the contract README.
- **Data minimization:** only a 32-byte digest is anchored. Detection IDs are opaque references; no coordinates or timestamps of the physical event are published.
- **Authority:** the sole write path is `register_evidence`, gated by the admin address fixed at deploy. Compromise of that key is the dominant risk; D5 uses a throwaway Testnet key and explicitly defers mainnet custody (multisig/HSM) to a later gate.
- **Immutability:** duplicates are rejected, so a compromised admin cannot silently rewrite an existing anchor in D5; a rewrite requires a new contract ID, which is publicly visible.
- **Read path:** `verify_evidence` is side-effect-free and unauthenticated by design, so third parties can audit without credentials.

### 8.4 Security Scan
- `cargo audit` is **mandatory and blocking** before any Testnet deploy and in CI. Output is attached to the Phase 5 report.
- `cargo clippy -- -D warnings` and `cargo fmt --check` gate the build.
- Dependency surface is one direct crate (`soroban-sdk`), pinned by `Cargo.lock`; no new transitive crates beyond the SDK's own graph.
- Contract-level checks: no `std`, no `unsafe`, no unbounded iteration, no `panic!` on user-controlled input in the read path, typed errors on the write path, explicit length validation, TTL extension on all persistent access.

### 8.5 Residual risk (accepted for D5)
- Admin key is a single Testnet identity (no multisig).
- No upgrade path; a defect requires redeploying under a new contract ID.
- TTL values must be confirmed against Testnet `max_entry_ttl` at bring-up; if the network maximum is lower, the constants are reduced and the policy documented.
