## Deviation 1 — `--output` flag does not exist (§2.1 correction)

§2.1 preferred command:
`python scripts/generate_odrm_data.py --n 500 --seed 7 --output benchmark/data/odrm_sample_500.parquet`

Actual CLI flags of `scripts/generate_odrm_data.py` (verified in Batch 6):
- `--n` (int, default 10000)
- `--seed` (int, default 7)
- `--out-dir` (Path, default `data/processed/odrm/v1`)
- `--compat-path` (Path, default `data/odrm_dataset.parquet`)
- `--created-at-base` (str, default `2026-01-01T00:00:00Z`)

**No `--output` flag exists.** The generator writes content-addressed batches under `--out-dir` and a compatibility copy at `--compat-path`.

**Revised Phase 4 command sequence:**
```powershell
python scripts/generate_odrm_data.py --n 500 --seed 7 --created-at-base 2026-01-01T00:00:00Z
Copy-Item -Path data/odrm_dataset.parquet -Destination benchmark/data/odrm_sample_500.parquet
```

`Copy-Item`, not `Move-Item`. The compatibility copy at `data/odrm_dataset.parquet` remains in place as the working compat path; the content-addressed canonical batch remains under `data/processed/odrm/v1/`. The sample is a snapshot, not a relocation.

`--created-at-base` is passed explicitly even though it equals the default. A future reproducer changing that flag would produce a different SHA-256 and incorrectly conclude the benchmark is not reproducible. Pin it.

## Deviation 2 — `MANIFEST.json` "first 500 rows" claim requires verification

Batch 1's `benchmark/data/MANIFEST.json` `notes` field states: *"The sample is the first 500 rows of the full dataset."*

This is **unverified**. `--n 500 --seed 7` and `--n 10000 --seed 7` may or may not produce identical first-500-row content depending on the generator's RNG strategy. Batch 6 confirmed the generator is deterministic same-seed, but did not confirm whether a 500-row run is a byte-for-byte prefix of a 10,000-row run.

**Phase 4 pre-flight check (mandatory):**

Before committing `benchmark/data/MANIFEST.json` to disk, run:

```powershell
python scripts/generate_odrm_data.py --n 10000 --seed 7 --created-at-base 2026-01-01T00:00:00Z --out-dir exports/verify_10k --compat-path exports/verify_10k.parquet
python -c "import pandas as pd; a = pd.read_parquet('benchmark/data/odrm_sample_500.parquet'); b = pd.read_parquet('exports/verify_10k.parquet').head(500); print('IDENTICAL' if a.equals(b) else 'DIFFERENT')"
```

If IDENTICAL: MANIFEST.json notes field ships as written in Batch 1.

If DIFFERENT: revise the notes field to: "The sample was generated independently with the same seed and generator; it is not a byte-for-byte prefix of the full dataset. Both are byte-for-byte reproducible from their own generation commands."

Either outcome is acceptable. Shipping a false claim is not. Verification is not optional.

Delete exports/verify_10k* after the check. Do not commit verification artifacts.

## Deviation 3 — generator writes its own manifest (name collision)

The generator writes data/processed/odrm/v1/_manifest.json on every run. Structure:
{schema_version, contract: {path, sha256}, batches: [{batch_id, file, sha256, row_count, column_count, source, generator, generator_version, seed, created_at_base, generated_at, compat_path, compat_sha256}]}

This file's name collides conceptually (not path-wise) with our benchmark/data/MANIFEST.json.

Resolution:

benchmark/data/MANIFEST.json — the release manifest. Hand-authored, ships with v1.0-benchmark. Reviewer-facing.

data/processed/odrm/v1/_manifest.json — provenance record. Machine-generated by the generator, stays under data/ (gitignored).

Do not merge. Do not rename either file. Two artifacts, two purposes. Only the generated_at_utc and files.odrm_sample_500.sha256 fields in the release manifest are populated from the generator's manifest after generation.

## Deviation 4 — generator append behavior affects Phase 4 sequencing

Batch 6 confirmed: each generator run appends a new immutable batch to _manifest.json rather than overwriting. data/processed/odrm/v1/ accumulates batches across runs.

Phase 4 must clean the working state before generating the sample. Otherwise the compatibility copy at data/odrm_dataset.parquet may correspond to a batch from a prior session, not the current seed-7/500-row run.

Pre-Command-1 step:

```powershell
Remove-Item -Recurse -Force data/processed/odrm/v1 -ErrorAction SilentlyContinue
Remove-Item -Force data/odrm_dataset.parquet -ErrorAction SilentlyContinue
```

Then run Command 1. Do not reorder.

## Dependency addition — scikit-learn lower bound

§2.3 did not constrain scikit-learn. Batch 3's revision (approved by CTO at Batch 3-revised audit) replaced mean_squared_error(..., squared=False) with root_mean_squared_error(...), which was introduced in scikit-learn 1.4.

New required dependency line for docs/BENCHMARK_REPRODUCTION.md and pyproject.toml:

scikit-learn >= 1.4 (for root_mean_squared_error); environment has 1.9.1.

pyproject.toml currently declares sklearn; no version bound is added there (avoid over-constraining the existing dev environment). The lower bound is enforced in BENCHMARK_REPRODUCTION.md Step 1 prerequisites. Add it as a one-line precondition in Phase 4 if it isn't already present from Batch 5 File 1 — Batch 5 already listed "scikit-learn 1.9.1 (minimum 1.4; provides root_mean_squared_error)", so no additional doc change is required. Recorded here for the audit trail only.
